## Source review findings

### C100 root identity

The stock C100 FDT audit records:
- model `deen`
- compatible sequence `qcom,msm8953-deen`, `qcom,msm8953-moto`, `qcom,msm8953`
- `qcom,msm-id = <0x125 0>`
- `qcom,board-id = <0x4d 0xc100>`

The current PVT1 wrapper has the correct MSM and board ID tuple, but its compatible sequence is `motorola,deen`, `qcom,msm8953`. This difference must be reconciled against the exact stock C100 FDT and Linux driver match tables before treating the candidate as compatible. Do not change compatible ordering or remove/add vendor strings merely to satisfy a schema.

### TSENS binding vs driver

The source-tree TSENS driver match table contains `qcom,tsens-v2` and maps it to `data_tsens_v2`; it does not contain a direct `qcom,msm8953-tsens` entry. The current DTS uses `qcom,msm8953-tsens` followed by `qcom,tsens-v2`, while the binding's v2 compatible list does not enumerate MSM8953. This explains the schema oneOf diagnostic, but it does not by itself prove that the v2 feature data, register layout, calibration and sensor numbering are correct for this board. Preserve the current compatible pair pending comparison with stock C100, driver feature data and calibration sources. A binding-only documentation change should be a separate patch after that evidence is established.

### Cache topology

The source contains eight Cortex-A53 CPU nodes with separate L1 instruction and data cache child nodes, and two shared L2 cache nodes. The successful structural gate verifies all eight CPU-to-L2 links and the L2 cache-level/unified properties in the compiled FDT. Do not mark L1 caches unified: that would misrepresent the split I/D topology. Schema status remains a separate review item.
